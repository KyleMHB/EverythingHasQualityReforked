## Verdict

The mod is worth maintaining. Its current architecture is a substantial improvement over a collection of broad quality patches: assignment and effects have separate policies, settings activate through a restart boundary, native components are retained, deferred recipes have isolated context, and optional adapters explicitly limit their supported schemas. Incremental maintenance is appropriate; a rewrite is not justified.

The principal release concern is confidence in the expanding integration surface. The seven focused check programs pass when their build directories are isolated, but the default test layout can silently run the wrong program. There are also concrete defects in signed role modifiers, conditional installation of the hauling safeguard, numeric-input validation, and package notice retention. None establishes that ordinary default gameplay is generally broken.

Both production builds passed during this review: 1.6 against `Krafs.Rimworld.Ref 1.6.4871`, and 1.7 against the installed `1.7.4984 rev1242` assemblies. This is compile compatibility. Earlier local evidence records a bounded 1.7.4982 gameplay smoke test, including settings, save/load and battery transitions; the current unfinished options interface and the complete feature set have not received equivalent runtime acceptance.

RimWorld 1.7 is currently an unstable-beta target according to [Ludeon's 12 October announcement](https://ludeon.com/blog/2026/10/announcing-the-waylith-engine-and-update-1-7/). Retaining 1.6 while validating 1.7 is appropriate. Harmony 2.4.2 matches the stable release identified by the [Harmony project](https://github.com/pardeike/Harmony/releases) and [RimWorld dependency releases](https://github.com/pardeike/HarmonyRimWorld/releases); upgrading solely for novelty is unnecessary.

## Architecture and behavior map

1. `ModSettings_QEverything` reads serialized configuration and migrates legacy values. `QualityConfigurationSession` separates active, saved and draft state.
2. `QualityCatalog` resolves supported definitions, captures native quality, and caches assignment/participation once at startup. `QualityRules` implements item → deepest category → group precedence with exclusion winning ties.
3. `Startup` schedules initialization after other startup callbacks. `QualityCompSync` adds owned quality properties while preserving existing quality components.
4. Recipe, construction, mining/harvest/gathering and fermentation hooks assign quality. `QualityOperationContext` scopes lazy recipe enumeration. Factory output exemptions protect selected native output policies.
5. Optional durability, energy, consumable, equipment/combat and linked-furniture adapters apply effects. Pure helpers own condition, energy, contribution and dose calculations. Most support decisions are cached by definition.
6. The current options windows edit drafts, show inherited rules/support reasons, preview presets and require Save/restart for activation.
7. Explicit scripts build versioned assemblies, stage a package, validate its layout and deploy only to a named external mod directory. Deployment was inspected but not run.

## Findings ordered by severity

### AUDIT-001 — High — Test projects can execute another check program

**Type:** confirmed validation-tooling defect. **Confidence:** High. **Affected:** all targets' assurance; independent of game version.

**Evidence:** all seven `Tests/*.csproj` files occupy the same directory and leave the SDK intermediate path at shared `Tests/obj/`. Their output directory also shares a framework/configuration directory. The generated apphost and NuGet assets can therefore be reused across different executable projects.

**Reproduction observed today:** ordinary `dotnet run --project Tests/FurnitureChecks.csproj` followed by ordinary `dotnet run --project Tests/SettingsChecks.csproj`, both with restore enabled, printed `8 linked furniture calculation checks passed.` twice. The Settings program should print its resolver/migration/isolation result. An earlier `--no-restore` sweep additionally produced missing-Harmony compile failures after a project with different restore assets; those failures were not mod compilation failures.

**Impact:** a green process exit can be credited to a test that never ran. This directly undermines release confidence and is more urgent than adding more calculation assertions.

**Recommendation:** give every project its own intermediate/project-extension and output directories, configured early enough for restore; add a small runner that verifies each expected program result and propagates failures.

**Verification:** run the projects consecutively in different orders without cleaning between them, including Furniture → Settings and dependency-free → Harmony projects. For this review, setting distinct `BaseIntermediateOutputPath` and `BaseOutputPath` per project produced all seven expected successful outputs. No project files were changed.

### AUDIT-002 — Medium — Negative production-role modifiers become large positive modifiers

**Type:** confirmed correctness defect. **Confidence:** High. **Affected:** assigned products/buildings on 1.6 and 1.7 when an ideology role supplies a negative production-quality offset.

**Evidence:** `Source/Quality_Generator.cs:121` casts the signed `RoleEffect_ProductionQualityOffset.offset` to `byte`, adds it to the tier and caps only the upper end. An executable arithmetic probe of this expression returned Legendary/tier 6 for Normal/tier 2 plus offset -1. Installed 1.7.4984 vanilla IL instead calls `QualityUtility.AddLevels(quality, offset)` with the signed integer.

**Impact:** a modded role intended to penalize production can instead push generated quality to the configured ceiling. Default positive vanilla role modifiers do not demonstrate this failure.

**Recommendation:** preserve signed arithmetic and use the native level-adjustment helper where compatible, followed by the existing configured bounds.

**Verification:** assert +1, -1, large positive and large negative offsets, then exercise an assigned product under a negative-offset test role. This audit confirmed the arithmetic error, not a full in-game reproduction. API comparison was against the locally installed authoritative game assembly.

### AUDIT-003 — Medium — Hauling safeguard is gated only on Stuff assignment

**Type:** confirmed coverage gap; gameplay consequence requires runtime reproduction. **Confidence:** High for the gate, Medium for resulting job behavior. **Affected:** 1.6/1.7 configurations with no assigned Stuff but quality-bearing non-Stuff construction/bill ingredients.

**Evidence:** `Source/Startup.cs:41` installs the queue comparison patch only when `QualityCatalog.AnyAssigned(QualityBucket.Stuff)` is true. `Source/Quality_Construction.cs:73–102` replaces a definition comparison with `Thing.CanStackWith`. Installed 1.7.4984 IL confirms the native queue method otherwise compares only `Thing.def`. Eligibility also supports Manufactured and other non-Stuff groups (`Source/Quality_DefUtility.cs`).

**Trigger:** exclude all Stuff, retain quality on a non-Stuff ingredient such as components, and queue collection of two same-definition stacks with different qualities for a suitable job.

**Impact:** the correction can be absent even though quality has created incompatible stacks. This can select an unmergeable next target; wasted travel or failed collection is a plausible consequence, not an observed loop in this review.

**Recommendation:** enable the safeguard for the actual set of potentially incompatible inputs, or install the narrow stack-compatibility check unconditionally after confirming its native behavior.

**Verification:** compare queued collection with Stuff disabled and only a non-Stuff ingredient assigned; include ordinary compatible stacks and already quality-bearing third-party inputs. Check both supported game versions. The default configuration normally enables Stuff and therefore installs this patch.

### AUDIT-004 — Medium — Prepared packages omit the inherited license notice

**Type:** confirmed packaging omission. **Confidence:** High. **Affected:** packages produced for both game versions.

**Evidence:** root `LICENSE` contains Cozarkian's copyright and MIT permission notice. `package-local.ps1:12–24` copies About, LoadFolders, selected Common content and DLLs, but no license. `validate-package.ps1:4–6` rejects any additional root entry, so simply adding a root LICENSE to a candidate would fail validation. The existing prepared package also lacks that file.

**Impact:** recipients of the prepared package do not receive the inherited notice carried by the source distribution. This is a concrete release-content defect; no legal interpretation is needed to fix it.

**Recommendation:** include the existing full notice in a documented package location and validate its presence. If using a root LICENSE, update both validation and the explicit deployment ownership rules so repeated deployments remain coherent.

**Verification:** build a fresh package, compare notice content byte-for-byte with the repository license, and validate/deploy it to a disposable workspace fixture. Do not use the real game installation for this check.

### AUDIT-005 — Low — Production numeric fields accept values that Save rejects

**Type:** confirmed inconsistency in the unfinished UI. **Confidence:** High. **Affected:** current working-tree options UI on 1.6/1.7.

**Evidence:** `Source/Window_QualityOptions.cs:243–248` advertises generic production float inputs as `0+` and allows up to `float.MaxValue`, except the special table factor. `Source/Quality_Configuration.cs:225` rejects production floats greater than 10.

**Trigger/impact:** enter 11 into a supply multiplier. The field is treated as valid and updates the draft; Save subsequently rejects the configuration. Inline guidance and close guarding do not explain the actual upper bound at the field.

**Recommendation:** share the allowed range between configuration validation and UI input/hints. Keep invalid partial typing in the edit buffer while preserving the last valid draft value.

**Verification:** exercise 0, 10, 10.01, blank/partial input, NaN and infinity; inline validity and Save must agree. This is a source-confirmed mismatch, not a completed visual/UI test.

### AUDIT-006 — Medium — Integration evidence does not cover the complete current release scope

**Type:** release-confidence gap, not a confirmed gameplay bug. **Confidence:** High. **Affected:** particularly 1.6 runtime, current 1.7 beta and the full Progression pack.

**Evidence:** the test projects link policy/calculation modules rather than the real game adapters. `.scratch/quality-plan/testing-notes.md` records a 1.7.4982 minimal-list smoke pass, but explicitly leaves crafting/mining/harvest, surgery/drugs, combat, multiplayer, performance and full Progression pending. Current UI changes postdate that candidate. Startup calls general `PatchAll` before component synchronization (`Source/Startup.cs:28–35,65`), leaving this core sequence dependent on successful runtime patch installation.

**Impact:** clean builds and helper tests do not prove actual IL matches, cache invalidation, Scribe lifecycles or provider interactions on every supported version. Current evidence cannot justify universal compatibility claims. A future patch-installation exception could interrupt later initialization; that is a risk, not an observed failure today.

**Recommendation:** complete a bounded acceptance matrix with exact game/mod versions and artifact hashes. Prioritize real recipe/construction/hauling, medicine/drug save/load and combat consumers, then selected Progression integrations. Record failures and unavailable adapters explicitly. Consider failure isolation only where an adapter can safely remain native.

**Verification:** run disposable minimal colonies for both versions, then small relevant integration subsets and one full-pack pass. Keep historical smoke results credited to their original artifact/version. No game launch, settings change or deployment was performed in this review.

### AUDIT-007 — Low — Obsolete UI/settings machinery obscures the maintained path

**Type:** maintainability improvement. **Confidence:** High for lack of internal callers. **Affected:** source maintenance, both versions.

**Evidence:** repository searches find no current callers of `QualityListCache`/`SearchableListUI` in `Source/Mod_SearchableList.cs`, the older population/numeric-entry helpers in `Source/Mod_SettingsUtility.cs`, `GetIndividualOrCategorySetting` at `Source/Quality_DefUtility.cs:243`, or `ValidBuffer` in the new window. `QualityCatalogEntry.Search` is built from extensive metadata (`Source/Quality_SettingsState.cs:148`) while the current browser filters labels directly. Legacy scalar state is duplicated in `ProductionSettings` and public static settings fields.

**Impact:** future work can target the wrong UI path, duplicate defaults can drift, and unused search text consumes startup memory. These are maintenance costs, not evidence of an FPS defect.

**Recommendation:** remove private/internal dead paths in a separate cleanup, or label deliberate compatibility surfaces. Preserve public members until external-call compatibility has been considered. Avoid changing default behavior during cleanup.

**Verification:** build both versions, search all references, and exercise the current settings flow. Do not delete retained public DefOf aliases merely because internal callers prefer the new declaration.

### AUDIT-008 — Informational — Public description and artifact identity trail local development

**Type:** publication/provenance observation. **Confidence:** High for observed differences; remote binary identity unverified. **Affected:** player expectations and support triage.

**Evidence:** the visible [Workshop description](https://steamcommunity.com/sharedfiles/filedetails/?id=3710884766) still describes the older configuration flow and directs broader effects to other mods. Local `steam-description.md` and the 18 October changelog describe the optional-effects expansion. `Source/Properties/AssemblyInfo.cs` keeps assembly/file versions at `1.0.0.0`.

**Impact/recommendation:** do not present local expansion behavior as verified released behavior. When an accepted candidate is published, synchronize its public description and keep a source/configuration/game-reference manifest with its hashes. A support-visible build identifier would help; changing assembly identity requires compatibility judgment. Publishing was not authorized or performed here.

**Verification:** compare the accepted source commit plus dirty-state status, packaged files and public download after publication. Current local 1.6 package DLL matches today's rebuilt DLL; the existing 1.7 package DLL differs from today's rebuild against 1.7.4984. A changed game reference can change deterministic output, so that mismatch alone does not prove stale source.

## Performance

No frame time, TPS, allocation or memory benchmark was run. The review found no demonstrated ongoing performance defect and no broad per-map/per-pawn periodic scanner in this source.

Positive evidence: runtime rule resolution is cached by definition; optional factors use dictionary/set checks and actual quality components; lists virtualize visible rows and invalidate filters/counts on revisions; harvest prerequisite discovery is cached; drug stages are copied only when their cached view changes; dose state uses weak tables.

Profiling candidates, not measured regressions:

- Quality separates resource stacks and can increase entities, hauling and storage pressure. Measure the same colony/stockpile with high-volume assignment enabled and disabled, recording stack count and TPS rather than attributing all changes to hook cost.
- Power output and battery reads receive hooks on frequently accessed consumers, including neutral paths. Measure CPU/allocation samples with effects disabled and enabled on a power-heavy colony.
- Startup builds the catalog and multiple per-effect support maps. Measure startup time and retained memory on the full definition set; unused catalog search data and repeated support bookkeeping are possible cleanup opportunities.
- Settings edits can rebuild counts/filter results and clone configuration for undo. Measure opening, scrolling and repeated bulk edits at the user's UI scale and full-pack definition count.

No third-party author's benchmark was transferred to this mod.

## Direct answers

- **Is it well written?** Mostly yes. The policy/state architecture and conservative effect adapters are strong; legacy duplication and dense UI code lower maintainability.
- **Are features badly implemented?** Specific edges are wrong: signed role offsets and hauling patch coverage. The default check runner is unreliable. The entire effects expansion is not thereby disproven.
- **Is it performant?** Its structure avoids obvious broad recurring scans, but actual large-colony performance remains unmeasured. Stack fragmentation is the main gameplay scaling concern.
- **Is it outdated?** No at the build/dependency level. It targets 1.6 and the current 1.7 beta runtime model; exact beta gameplay acceptance needs continued work.
- **Are published claims accurate?** The visible older claims broadly fit the older feature set. Public copy does not yet describe the local expansion, and neither copy nor metadata proves that the remote binary matches this tree.
- **Five highest-value improvements:** trustworthy test isolation; signed role arithmetic; correct hauling safeguard coverage; complete versioned runtime acceptance; coherent release contents/provenance, starting with the license notice. Numeric-bound consistency is a small accompanying UI fix.
- **Is continued maintenance worthwhile?** Yes. Repair the bounded defects and strengthen evidence around the existing adapters; retain the architecture.
